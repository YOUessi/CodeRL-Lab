# 正式数据集方案 v1

> 日期：2026-10-06  
> 对应任务：DATA-001  
> 状态：设计已确定，适配器尚未完成。

## 1. 目标

CodeRL-Lab 后续要比较监督微调（SFT）和可验证奖励强化学习（RLVR/GRPO），因此数据集必须同时满足：

1. 有可自动执行的测试；
2. 可以严格区分训练可见测试和隐藏测试；
3. 有足够任务数量和难度跨度；
4. 能支持多次采样与 Pass@k；
5. 尽量降低训练/评测污染；
6. 不为了迁就当前执行器而人为只保留某一种题型。

## 2. 数据分层

### 2.1 APPS：训练池与内部留出池

来源：

- Hugging Face：<https://huggingface.co/datasets/codeparrot/apps>
- 原论文：APPS: Measuring Coding Challenge Competence With an Open-Access Dataset（NeurIPS 2021）

用途：

- 监督微调训练数据；
- 强化学习训练任务；
- 内部验证和难度分层；
- 奖励函数、动态采样和能力边界实验的主任务池。

选择原因：

- Python 代码解决方案可直接用于监督微调；
- 自带输入输出测试，可形成可验证奖励；
- 含 introductory / interview / competition 难度信息；
- 数据规模足够支持训练、验证和留出实验。

限制：

- 数据较老，不能把 APPS 测试集宣传为对现代模型“无污染”；
- 部分任务测试数量不足，历史工作已经指出可能出现错误解法通过测试的假阳性；
- 大量任务是标准输入/标准输出程序，不是函数调用；
- 原始测试格式存在多种结构，适配时必须显式验证，而不能静默猜测。

因此：

**APPS 是训练和内部实验数据源，不承担“绝对无污染外部泛化”这一角色。**

## 3. EvalPlus：稳健性回归评测

来源：

<https://github.com/evalplus/evalplus>

用途：

- HumanEval+ / MBPP+ 作为执行器与模型代码能力的外部 sanity check；
- 利用增强测试检查“公开测试通过但隐藏行为错误”的情况；
- 后续用于 SFT / RL 的补充对照。

限制：

- HumanEval 和 MBPP 都属于老基准；
- 对现代基础模型存在较强潜在污染风险。

因此：

**EvalPlus 不进入训练，不作为主要科研结论的唯一外部评测集。**

## 4. LiveCodeBench：外部时序代码评测

来源：

<https://github.com/LiveCodeBench/LiveCodeBench>

优点：

- 按时间持续加入竞赛代码题；
- 支持代码生成等多种评测；
- 题目带时间信息，比固定老基准更适合讨论污染。

当前项目拟优先使用：

`code_generation_lite`

作为外部代码生成评测。

### 重要污染声明

截至本方案撰写时，公开的 LiveCodeBench v6 覆盖题目时间到 2025-04 左右；同时我们没有找到 Qwen3 官方公开的精确预训练数据截止日期。

所以对于 Qwen3：

```text
LiveCodeBench v6 相对 Qwen3 的污染状态 = 未知
```

项目文档中**不得**写成：

```text
Qwen3 上绝对 contamination-free
```

只能表述为：

- 时间标注外部评测；
- 相比老基准更便于分析污染；
- 但相对具体基础模型的绝对污染状态未知。

Qwen3 官方背景资料：

<https://qwenlm.github.io/blog/qwen3/>

## 5. 为什么第一阶段不优先 CodeContests

CodeContests 同样适合竞赛编程研究，但第一阶段不作为主训练源，原因不是它质量差，而是：

- APPS 的 Python 数据和难度字段更方便快速建立 SFT / RL 数据流水线；
- 我们当前目标是先验证后训练方法，而不是先解决大规模多语言竞赛工程；
- 等双模式执行器和数据管道稳定后，可以把 CodeContests 作为第二个训练分布，研究跨数据集泛化。

## 6. 任务协议必须支持两种模式

当前 EXP-001 只支持函数调用：

```text
函数 + JSON 参数 → 返回值
```

正式数据阶段升级为：

### 模式 A：函数调用（function）

示例：

```python
def add(a, b):
    return a + b
```

测试：

```json
{
  "args": [1, 2],
  "kwargs": {},
  "expected": 3
}
```

### 模式 B：标准输入输出（stdin_stdout）

候选是完整 Python 程序：

```python
a, b = map(int, input().split())
print(a + b)
```

测试：

```json
{
  "stdin": "1 2\n",
  "expected_stdout": "3\n"
}
```

这样我们不会为了适配旧代码而丢掉 APPS 大量标准输入输出任务。

## 7. 公共测试 / 隐藏测试策略

### 原则

强化学习阶段只能看到：

- 题目描述；
- 起始代码（若有）；
- 公共测试形成的奖励。

隐藏测试：

- 不进入提示词；
- 不进入训练奖励；
- 不进入动态采样的训练时成功率；
- 只用于最终评测与泛化判断。

### APPS 内部拆分

适配器必须先统计每题有效测试数量。

第一版建议：

- 有效测试少于 4 个：不进入正式 RL 主实验；
- 4–5 个测试：1 个公共，其余隐藏；
- 6–9 个测试：2 个公共，其余隐藏；
- 10 个及以上：最多 20% 公共，其余隐藏；
- 拆分由 `task_id + 固定 seed` 决定，保证可复现。

这里的阈值是 **v1 工程规则，不是科研结论**。接入 APPS 后必须先统计测试数量分布，再决定是否调整。

## 8. 输出比较

标准输入输出模式第一版比较规则：

1. 统一 CRLF / LF；
2. 每行去掉行尾空白；
3. 去掉文件首尾纯空白行；
4. 中间行结构不改变；
5. 不做模糊语义匹配。

后续 APPS 适配器如果发现题目需要：

- 浮点容差；
- 多个等价输出；
- 顺序无关集合；

必须显式引入判题策略，不能偷偷把严格比较改成宽松比较。

## 9. 正式实验分层

最终至少保留三层：

```text
训练层：
APPS train 子集
    ↓
内部验证层：
APPS 留出任务 / 留出测试
    ↓
外部评测层：
EvalPlus + LiveCodeBench
```

这样可以分别回答：

- 在同分布任务上学到了什么；
- 对未参与训练的 APPS 任务是否泛化；
- 对外部代码基准是否泛化。

## 10. 数据污染记录

每个正式实验必须记录：

- 数据集名称和版本；
- 下载日期；
- 原始 split；
- 过滤规则；
- 任务 ID 列表或其哈希；
- 公共/隐藏测试拆分 seed；
- 基础模型与精确 revision；
- 已知或未知的训练数据截止信息；
- 不能确认无污染时，明确写“未知”。
